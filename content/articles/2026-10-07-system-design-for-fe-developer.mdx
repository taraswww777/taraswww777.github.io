    Когда мы говорим «системный дизайн» в контексте фронтенда, часто возникает путаница. Кажется, что это про бэкенд: микросервисы, очереди,
    шардирование баз данных. На самом деле системный дизайн фронтенда — это проектирование клиентской архитектуры: слои приложения, управление
    состоянием, кэширование, роутинг, обработка ошибок, производительность при росте объёма данных.

    Цель — заложить структуру, которая не разваливается, когда количество компонентов переваливает за сотню, а файлов — за тысячу.

    Проблема в том, что между «понимать архитектуру» и «уметь её проектировать» — пропасть. Обучение должно мостить эту пропасть через конкретный
    проект, где каждый артефакт имеет измеримый результат.

    ## Учим через реальный проект

    В качестве учебного полигона возьмём [Docs Tasks](https://github.com/taraswww777/vscode-plugin-docs-tasks) — расширение для VS Code и Cursor,
    которое работает с файлами задач в формате <code>TASK-*.md</code> с YAML frontmatter. Плагин показывает таблицу и канбан по этим файлам,
    поддерживает сохранённые виды с фильтрами и редактирует метаданные без изменения основного текста задачи.

    Почему этот проект:

    - **Достаточно сложен** — есть парсинг, состояние, рендер, drag-and-drop, файловый ввод-вывод.
    - **Достаточно мал** — один человек может охватить всю архитектуру целиком.
    - **Реальный** — плагин опубликован в Marketplace, им пользуются.

    ## Что такое системный дизайн FE

    Системный дизайн фронтенда отвечает на вопросы:

    - **Слои**: где живёт парсинг файлов, где рендер, где бизнес-логика?
    - **Состояние**: как хранится индекс задач? Кто его обновляет?
    - **Потоки данных**: что происходит, когда пользователь перетаскивает карточку в канбане?
    - **Контракты**: какой формат у файла <code>TASK-*.md</code>? Какие поля обязательны?
    - **Обработка ошибок**: что если YAML невалиден? Если файла нет? Если нет прав на запись?
    - **Производительность**: что будет при 1000 файлов? При 10 000?

    В контексте Docs Tasks это выглядит так: плагин читает файлы из каталога <code>docs/tasks/</code>, парсит YAML frontmatter между первыми
    линиями <code>---</code>, строит индекс задач, рендерит таблицу или канбан по полю <code>status</code>, обрабатывает действия пользователя
    (перетаскивание карточки → обновление <code>status</code> и <code>updated</code>) и записывает изменения обратно в файл.

    ## Проектирование и реализация — не одно и то же

    Это ключевое различие, которое должен усвоить разработчик.

    **Проектирование** — фиксируем, как система должна работать: сценарии, контракты, потоки данных, правила. Результат — артефакты (диаграммы,
    таблицы, спецификации).

    **Реализация** — пишем код под зафиксированные решения. Результат — работающая функциональность.

    ### Пример из плагина.

    Спроектировать — описать, что перетаскивание карточки из колонки <code>in_progress</code> в <code>done</code> должно обновить
    поле <code>status</code> в YAML и дату <code>updated</code> без изменения основного текста задачи.

    Реализовать — написать код, который читает файл, парсит frontmatter, обновляет поля и записывает обратно, сохранив оригинальное форматирование.

    Без проектирования разработчик сразу бросается в код и обнаруживает проблемы на поздних этапах: оказывается, нужно сохранять комментарии между
    полями, или что порядок полей имеет значение, или что файл может быть открыт в редакторе и нужно как-то синхронизировать изменения.

    ## Артефакты по итогам проектирования

    Минимальный набор, который должен уметь производить FE-разработчик:

    ### Постановка задачи и scope

    Что делаем, что не делаем. Для плагина: работаем с <code>TASK-*.md</code> в указанном каталоге. Не работаем с произвольными markdown-файлами. Не
    реализуем совместное редактирование.

    ### Контракт данных

    Формат файла <code>TASK-*.md</code> с YAML frontmatter между <code>---</code>.
    Поля: <code>id</code>, <code>title</code>, <code>status</code>, <code>priority</code>, <code>assignee</code>, <code>updated</code> и т. д. Типы,
    обязательность, значения по умолчанию.

    ### Диаграмма компонентов и потоков

    Как данные движутся по системе: файловая система → чтение файлов → парсинг YAML → индекс задач → рендер таблицы/канбана → действие пользователя →
    обновление YAML → запись в файл.

    ### Структура слоёв и правила импортов

    Где живёт парсинг (читальный слой), где рендер (слой представления), где бизнес-логика (обновление статусов). Правило: слой рендера не читает
    файлы напрямую, а работает с индексом.

    ### Таблица состояний

    Статусы задач: <code>todo</code>, <code>in_progress</code>, <code>done</code>, <code>blocked</code>. Переходы между ними. Какие действия доступны
    в каждом состоянии. Это конечный автомат, и его нужно зафиксировать до кода.

    ### Критические сценарии (acceptance criteria)

    Что обязательно должно работать:

    1. Успешное перетаскивание карточки → обновление <code>status</code> и <code>updated</code>.
    2. Ошибка парсинга YAML → сообщение, карточка не падает.
    3. Пустой каталог задач → нормальное пустое состояние, не ошибка.
    4. Файл не найден при записи → обработка и сообщение.

    ### План производительности

    Что будет при 1000 файлов? Нужно ли индексировать асинхронно? Кэшировать парсинг? Виртуализировать список? Это не преждевременная оптимизация —
    это проектирование с учётом масштаба.

    ## Обучение через артефакты

    Каждый артефакт — это не документация ради документации, а тренирующий материал, который одновременно развивает навык и приносит пользу в проекте.

    Последовательность обучения:

    1. **Постановка задачи и ограничения** — учит ставить рамки. Результат: короткий документ с scope.
    2. **Диаграмма компонентов и потоков** — учит видеть систему целиком. Результат: диаграмма, где видно путь от файла к канбану.
    3. **Контракт данных и слои** — учит проектировать до кода. Результат: спецификация формата и схема слоёв.
    4. **Критические сценарии** — учит думать о тестах заранее. Результат: список сценариев с ожидаемым поведением.
    5. **План производительности** — учит думать о масштабе. Результат: оценка узких мест и решения.

    Каждый шаг — измеримый результат. Не «я почитал про архитектуру», а «я зафиксировал, как данные идут от файла к канбану».

    ## Декомпозиция работ

    FE-разработчик должен уметь разбивать спроектированное на атомарные задачи с измеримым результатом. Принцип: одна задача — один проверяемый
    результат с Definition of Done.

    Декомпозиция эпика «Канбан» для плагина Docs Tasks:

    1. **Чтение и индексация файлов** <code>TASK-*.md</code> из <code>docs/tasks/</code>. DoD: индекс строится, логируется количество найденных
    файлов.
    2. **Парсинг YAML frontmatter** в типизированные объекты. DoD: поля доступны как свойства объекта, невалидный YAML не валит весь индекс.
    3. **Рендер колонок канбана** по полю <code>status</code>. DoD: карточки группируются по статусам, колонки в правильном порядке.
    4. **Drag-and-drop карточек** с обновлением <code>status</code> и <code>updated</code> в YAML. DoD: перетаскивание меняет файл, текст задачи
    сохраняется, форматирование не ломается.
    5. **Сохранённые виды с фильтрами** — вкладки сверху. DoD: фильтр применяется, вид сохраняется, при перезапуске восстанавливается.
    6. **Обработка ошибок** — файл не найден, невалидный YAML, нет прав на запись. DoD: каждая ошибка обрабатывается, пользователь видит понятное
    сообщение.
    7. **Тесты на критические сценарии** — успешное перетаскивание, ошибка парсинга, пустой каталог. DoD: тесты зелёные, покрытие критических путей.

    Каждая задача самостоятельна, имеет понятный DoD и может быть взята в работу независимо. Это особенно важно при обучении, где разработчик
    параллельно реализует функциональность в другом проекте — ему нужно чётко понимать, что именно он делает на текущем шаге.

    ## Итог

    Обучение системному дизайну FE-разработчика — это последовательное освоение четырёх навыков:

    1. **Спроектировать** — описать, как система работает, до написания кода.
    2. **Зафиксировать артефакты** — контракт данных, диаграммы, сценарии, таблицы состояний.
    3. **Декомпозировать на задачи** — разбить на атомарные части с DoD.
    4. **Реализовать с тестами** — написать код, который проходит критические сценарии.

    Каждый этап имеет конкретный измеримый результат, а не абстрактное «понимание архитектуры».
    Проект [Docs Tasks](https://github.com/taraswww777/vscode-plugin-docs-tasks) оказывается удачным полигоном:
    достаточно сложный, чтобы системный дизайн был нужен, и достаточно компактный, чтобы один разработчик мог его охватить.
